## Challenges

### Vocabulary Drift (4 of 8 stories affected)
Stories 3.1, 3.4, 3.5, 3.6 all rewrote SPARQL templates because specs assumed `oslo-educ:` predicates that don't exist in Oxigraph. The actual namespace is `poc-pod0.edu/vocab/` as produced by `oslo_mapper.py`. Each story discovered this independently before handoff notes caught up.

**Root cause:** Story specs written against the theoretical OSLO vocabulary (Story 2.1 schema contract) rather than the actual predicates in the live data store.

**Prevention:** Add "vocab reality check" step — query actual Oxigraph predicates before writing any new SPARQL template.

### CSS Environment Variable Complexity
The three-variable model (`CSS_IDENTIFIER_URL` + `CSS_CONNECT_URL` + `CSS_IDENTIFIER_HOST`) was discovered in Story 3.1 and rediscovered in Story 3.4. Docker-internal vs host-side access patterns require different URLs for the same service. Documented but keeps surprising.

### NFR Latency Expectations vs Reality
Spec numbers written for local uncontainerized setup:
- SPARQL: spec 500ms → reality 2s (containerized Oxigraph + ACL round-trip)
- Hybrid: spec 2s → reality 10s/student (OpenRouter embedding API adds 1-7s variance)
- Story 3.7 integration tests had to relax thresholds to pass against live stack

### Pipeline Opacity (→ Story 3.7.1 Side-Quest)
The ~48-minute pipeline regen is a black box. CSS pods accumulated stale data between `--wipe` runs (119 success/score mismatches from pre-fix troll data). The fix (Story 3.7 P1: leaf-first LDP DELETE with dynamic pod discovery + recursive container traversal) was significant work that could have been avoided with better pipeline observability.

Story 3.7.1 was born from this frustration: JSONL event stream + `rich.live` TUI dashboard. Validated Rich TUI as the demo UI pattern — pivoting away from FastAPI+HTMX for Epic 6.

### Project Lead Navigating Blind
Nicolas's key insight: "I'm like Isabelle — navigating blind, crossing fingers, trusting the system and the tests + review phases because we don't have the dashboard yet."

The meta-symmetry is significant: the project lead experiences the same opacity as the policy advisor persona. This directly drove the 5→6→4 resequencing decision.

## Anagnorisis — The Major Discovery

### What happened

During Epic 3 (around Stories 3.5-3.6), Nicolas explored the Ayoub-Isabelle relationship deeper and developed the "Anagnorisis" narrative — a camp/food service scenario that crystallizes consent-as-architecture:

**Step 1 — The Two Pods:** Ayoub's personal pod (identity, food/medical data, school records) and the camp pod (aggregate, anonymous). Nothing flows between them yet.

**Step 2 — The Consent Grant:** The camp declares who they are, what they want (attendance + food regime count), why (funded program rapportage), and what happens if refused (data excluded from aggregate). Ayoub + guardian approve or deny. A receipt is written to Ayoub's pod.

**Step 3 — Lunch Service (Double-Aveugle):** Kitchen receives food regime counts (gluten-free: 3, nut allergy: 2, standard: 12) but not WHO. Ayoub's phone shows a food token — tap to approve, auto-revokes after lunch. No single actor holds both halves. Everything dissolves after lunch.

**Step 4 — The Policy Query:** Isabelle queries the camp pod weeks later — not Ayoub's pod. The data was already a number before she asked. Individual data was never there.

### Design Principles Crystallized

1. **Consent as Architecture** — The boolean ACL flag becomes a dereferenceable contract with 4 questions: Who is asking? What will they see (and NOT see)? Why are they asking? What if you say no?

2. **Structural Anonymization at Ingest** — The GROUP BY fires when data enters the camp pod, not when Isabelle queries. By the time she asks, the data is already a number.

3. **Bidirectional Accountability** — Every data flow generates a readable receipt for the person whose data flowed. The troll audits both directions simultaneously.

4. **Ephemeral Consent (Double-Aveugle)** — Time-scoped, purposeful, self-destructing tokens. The food token pattern generalizes: any consent can carry auto-revocation.

5. **Civic Signal via Revocation** — Consent revocation is not a system event. It's liquid democracy at the data layer. If revocations spike, Isabelle sees the pipeline go dry — distrust made legible.

## Architectural Pattern: Ontology-as-Plugin (Post-POC Vision)

### The Insight

OSLO is ONE ontology for ONE domain (Flemish education via xAPI). The pod is domain-agnostic. The three-layer stack — Pod (storage + ACL) → Graph (triples + provenance) → Vector (embeddings + search) — is domain-neutral infrastructure. Domain specificity lives in the service that reads and writes.

### Why This Matters Now

The vocabulary drift (4 of 8 stories) was a symptom: we treated `oslo-educ:` as architecture, but the architecture is ontology-agnostic. `poc-pod0.edu/vocab/` is the PoC's domain ontology. The fix is not to hardcode a better namespace — it's to make the ontology a declared dependency of the ingestion service.

### Domain Variants Identified

| Domain | Isabelle Analog | Ontology | Status |
|---|---|---|---|
| **Education (PoC)** | Regional policy advisor (Brussels-Capital) | OSLO/poc-pod0 via xAPI | Active — Epics 1-6 |
| **Medical** | Health insurance / eHealth aggregate | HL7 FHIR | Post-POC backlog (captured 2026-03-20) |
| **Maker/Hobby** | Erasmus+ assessor / national agency | Open Badges / credentialing | Post-POC backlog (captured 2026-03-25) |
| **Family** | N/A — consent within family boundaries | Schema.org / custom | Post-POC backlog (captured 2026-03-25) |
| **Work** | HR / skills portfolio | European Learning Model / ESCO | Post-POC backlog (captured 2026-03-25) |
| **Liquid Democracy** | Governance automation for collectives | Custom / civic ontology | Post-POC backlog (captured 2026-03-25) |

### Pod = Personal Locker

The pod is a personal locker — portable, searchable, W3C + 5-star LOD compliant. Services load the adhoc ontology for the adhoc context. Anyone can build services on top of the pod infrastructure: input/output UI for specific purpose and domain.

**Note:** Divorced parents / split consent authority is a medical/family domain edge case. Architecturally possible via Solid ACL smart-contract patterns, but too many variables for the PoC. Fatima in our PoC = mother of 2 kids in different schools (not 2 parents for 1 kid).

3. **Capstone integration test:** Epic 4 (Marc's transfer) becomes the last epic — the real test drive implementing the final use case WITH the dashboard running. If anything breaks, it's visible in real time.

4. **Anagnorisis enrichment:** Epic 5 is where consent-as-architecture lives. The Anagnorisis narrative (4-question consent contract, access receipts, ephemeral tokens, tombstone revocation, civic signal) enriches Epic 5 stories directly.
